# Agent Store 智能商城答辩逐页讲稿

建议总时长：8-10 分钟。每页只讲一个结论，不逐字朗读页面。

## 1. 封面：Agent Store 智能商城

老师好，我们的项目不是只做一个商城页面，而是把注册、商品、搜索、交易、AI 导购、部署和测试串成可演示闭环。今天重点回答三个问题：系统如何完成真实交易，Agent 为什么不是普通聊天框，工程结果如何被验证。

## 2. 目录：先讲闭环，再讲亮点和证据

汇报先从定位与架构开始，再快速覆盖五大模块；中段集中讲 AI、并发和工程化亮点；最后用真实界面、测试数字、已知局限和交付材料收束。页面底部把六项评分标准显式列出，让评委一开始就知道每个评分点会在哪里被证明。

## 3. 项目定位：15 天实训完成全流程

项目定位是企业实训系统，不追求生产级双十一架构。必须交付五大核心模块、四个容器服务和一个 MySQL 数据源，重点证明软件工程全流程、Agent 集成和可复现部署能力。

## 4. 总体架构：业务边界清晰

Vue3 只访问主后端和 Agent；Spring Boot 是用户、商品、订单等业务数据的唯一写入口；Agent 独立使用 Python 和 LangChain，只通过受限 REST 接口访问业务数据，仅直接维护自己的会话、偏好和知识库表。

## 5. 技术选型：满足大纲且不过度设计

前端使用 Vue3 组合式 API，后端使用 Spring Boot 3.3、Security、JWT 和 JPA，AI 服务使用 FastAPI、LangChain、SQLAlchemy，部署使用 Docker Compose。没有引入网关、注册中心、MQ 或 Redis，避免偏离实训主链路。

## 6. 数据库设计：3NF 与历史事实并存

核心业务按职责拆表，关系满足第三范式。用户域、商品域、交易域、运营行为和 Agent 专属数据边界清晰，`user_preference` 只归 Agent 记忆域。`order_item` 中的商品名和价格是下单时刻的事实快照，用于保证商品后续改名、改价不影响历史订单，因此是有明确业务语义的合理非规范化。

## 7. 功能全景：核心模块之外还有体验增强

五大必验收能力是用户认证、商品、搜索、订单和 AI 助手；购物车归订单模块。认证能证明 401、JWT 和 BCrypt，搜索能证明关键词、排序和分页，订单能证明事务、状态机和取消回补，AI 能证明工具调用与记忆。收藏、评价、优惠券、售后和后台属于增强能力。

## 8. 亮点一：偏好记忆进入首页推荐闭环

用户在对话中表达偏好，系统提炼标签写入 `user_preference`；新会话读取高权重标签注入提示词；首页推荐接口也消费同一偏好。这样“记住用户”会影响真实页面，而不只是聊天回复。

## 9. 亮点二：轻量 RAG 提供事实约束

知识库采用 MySQL 知识块，没有引入向量数据库。运行态共有 88 个知识块，包括商品、评价和 FAQ。`search_knowledge_base` 工具在需要时检索这些事实，补充评价和规则依据，减少无依据回答。

## 10. 亮点三：结构化 Agent 工作台

用户提出户外跑步装备需求时，系统先只追问缺失预算；拿到预算后检索真实商品和知识，生成不超过三件的购买方案。`ChatUi` 稳定返回任务步骤、商品卡、操作按钮和数据来源；真正加购前必须再次确认。最新版烟测覆盖同步接口、SSE 流式事件、新会话隔离和确认加购。

## 11. 亮点四：可诊断的前端性能工程

项目建立了页面内性能 HUD、动效开关和真实 Chrome CDP 脚本，但尚未形成完整真实设备 FPS 矩阵，因此不展示无法复现的性能数字。这里展示的是诊断能力和工程严谨性。

## 12. 亮点五：并发库存安全

扣库存 SQL 同时检查库存和版本，并在原子更新中扣库存、增加销量和版本号；订单、订单项、购物车清理都在 `@Transactional` 中。页面展示的是最近一次 100 抢 80 验收留证结果：成功 80、失败 20，最终库存 0、销量 80、版本 80；答辩前仍应在清洁数据下复跑并保存终端和 SQL 双证据。

## 13. 用户端实景：商品和订单都来自真实接口

左侧展示登录态商品中心，右侧展示 AI 查询真实订单。Agent 不信任前端传入的用户 ID，而是先用用户 JWT 调主后端确认身份，再使用内部服务密钥访问受限订单接口。

## 14. 交易闭环实景：购物车到订单状态

购物车支持数量调整和勾选结算，订单支持优惠计算、模拟支付、取消、发货、确认收货和再次购买。取消订单与售后审核涉及库存回补，当前实现使用原子更新并有集成测试覆盖。

## 15. 管理端实景：运营能力统一收口

管理端包括数据看板、商品管理、订单发货、售后审核、用户反馈和 Excel 导出。它和用户端共享同一业务后端，普通用户调用管理员接口会返回 403。

## 16. 验证结果：可以支撑现场演示

2026-07-10 重新执行结果是：Maven 20 个测试全部通过，前端生产构建通过，最新版 Agent 端到端烟测通过；并发结果已有运行态留证，Docker 四个服务正常运行。前端构建的大 chunk 警告在局限页如实说明。

## 17. 部署与日志：一键启动，可定位问题

Compose 编排 MySQL、后端、Agent 和 Nginx 前端，页面箭头表示启动依赖顺序，不代表业务调用方向。容器通过服务名通信，密钥通过环境变量注入。排障顺序是先看容器状态，再看后端和 Agent 日志。

## 18. 当前状态：完成与局限同时讲清楚

主链路和核心验收已经完成，但前端仍有大 chunk 需要拆分，搜索当前主实现是 `LIKE`，真实设备性能矩阵尚未补齐，Git 分支和 PR 证据偏弱。这些是教学简化和生产化之间的真实差距。

## 19. 协作与 AI 辅助：用证据说明贡献

按工作包展示可核查交付：用户模块看安全测试，商品模块看接口和页面，订单模块看事务与并发，AI 模块看工具和烟测，文档模块看完整材料。Claude Code/Codex 参与需求拆解、代码生成、缺陷排查和文档审计，过程记录见 `docs/ai-development-record.md`；AI 加速产出，人负责边界设计、事实核对和最终验收。

## 20. 结束页：演示顺序与提问引导

我们的交付不是一组孤立页面，而是一条可运行、可解释、可验证的智能商城闭环。现场演示建议依次完成：登录、搜索、加购下单、AI 查询订单、AI 生成购买方案并确认加购、后台查看订单和日志。

## 现场高频追问速答

1. 为什么 Agent 独立成 Python 服务？
   因为 LangChain 生态成熟，同时把 AI 推理和主业务事务边界隔离；Agent 挂掉不影响商城交易主链路。

2. 为什么不会超卖？
   原子 SQL 同时检查 `stock` 和 `version`，影响行数为 0 就让事务失败回滚；100 抢 80 的运行结果也验证了这一点。

3. Agent 怎么知道用户订单？
   先用用户 JWT 调 `/api/user/profile` 确认身份，再通过内部服务密钥调用受限订单接口，不能直接相信前端传入的 `userId`。

4. 长短期记忆有什么区别？
   短期记忆按 `session_id` 保留最近对话并落到 `agent_conversation`；长期记忆写入 `user_preference`，跨新会话读取。

5. 为什么说不是普通聊天框？
   因为 Agent 会选择工具读取真实商品和订单，返回结构化商品卡和任务状态，并且对加购这种写操作要求用户二次确认。

6. 最大不足是什么？
   前端包体、搜索实现、真实设备性能矩阵和 Git PR 证据仍可加强；项目明确定位为教学实训，不把简化方案包装成生产级能力。
